Mia by Tanishq · Gifting Collection Page

Gifting Page Handover

Why the page is built the way it is, and the logic behind how each section actually works.

saakshi-m11.github.io/Mia-Gifting-Page

The short version: a person buying jewellery as a gift is deciding on someone else's behalf, often blind on size and taste, so this page's job is to remove that uncertainty rather than just display product. Six visitor types, from someone buying last-minute to someone shopping weeks ahead to someone buying for themselves, each get a specific, evidenced answer to what would otherwise stop them from completing a purchase. Every section can be traced back to Mia's own order data, a recorded customer complaint, or an evidenced gifting behaviour, not a stylistic guess. Everything below is organised by where it sits in the actual buying journey and collapsed by default, expand any persona or section for the full reasoning behind it.

01Visual & Creative Direction

Our call

The product photography deliberately uses clean, minimal backgrounds instead of busy or colourful product backdrops. Competitor cards in this category often use decorative or coloured backgrounds, which reads closer to mass market. Clean backgrounds keep focus on the piece itself and match the "considered high value purchase" positioning the whole page is built around.

02Who's Actually Landing On This Page

Six visitor types, built from Mia's own order data, search data and complaint records, plus documented Indian jewellery gifting behaviour where Mia's own data doesn't cover it. Click a name to expand.

The Anxious Gifter ▾

What they need to see: a way to buy blind, on size, on taste, without it becoming a costly mistake if they get it wrong.

This is the default emotional state for anyone buying jewellery for someone else, not an edge case. Sizing and exchange difficulty are Mia's own two most recurring recorded complaints, and gift giving anxiety research (Wooten, 2000) shows this anxiety peaks specifically with close relatives, the exact recipient profile for most jewellery gifts.

The Late Planner ▾

What they need to see: speed over choice. They've run out of time to deliberate and need something that will definitely arrive in time.

Gold and silver coin are Mia's #1 and #2 site search terms, ahead of rings, the clearest evidence that a real share of visitors want the zero decision, fastest delivery option, not more curation.

The Early, Occasion-Aware Planner ▾

What they need to see: confidence that if they order now, it will land on the exact right day, not just "within a few days."

Mia's own order data shows purchases peaking 8 to 11 days ahead of Rakhi and Valentine's Day. This is a deadline aware planner, not a last minute panic buyer, and the page underserves them if it only optimises for urgency.

The Self-Gifter ▾

What they need to see: that buying for herself belongs here too, not a separate, apologetic corner of the site.

Mia's own brand positioning has been shifting toward self purchase, not just gifting to others. CaratLane's Self Rewards collection is the proven precedent for treating this as a first class path rather than an afterthought.

The Cold / Unfamiliar Visitor ▾

What they need to see: within seconds, that Mia is a legitimate, distinct jewellery brand, not assumed familiarity just because it sits under Tanishq.

Mia's own GA data shows a large "Awareness Only" cohort (15M+ DemandGen sessions, close to 0% CVR) with no prior brand context. Tata/Tanishq trust doesn't automatically transfer to "Mia" by name for someone who has never seen this specific sub-brand before.

The Consultative Decider ▾

What they need to see: an easy way to involve someone else in the decision, a sister, a partner, without screenshotting five product pages manually.

Referral and WhatsApp driven traffic converts at roughly 23x the site average on Mia's own property, the clearest signal available that this decision is frequently made in consultation, not solo.

Why this doc exists: the design shows what each section looks like once it's working. It doesn't say what decides which products appear in the Gift Finder, what happens when a filter returns zero results, or what the hero banner should do the day after an occasion passes. This doc is that missing layer, written as logic and rules, not code, so a developer can build each section correctly the first time and a reviewer can check it against something concrete rather than "does it look right."

01Section-By-Section Build Logic

In page order. Each module covers: what it needs as input, the rules that govern its behaviour, and the edge cases to handle explicitly rather than discover later.

1

Hero Banner

▾
Purpose

First-viewport banner. Needs to change with the occasion calendar (Rakhi, Valentine's, Diwali, wedding season, etc.), not stay static year-round.

Data needed
  1. A list of "banner campaigns," each with: creative (image/video), headline, subhead, primary CTA text and destination, secondary CTA text and destination, an active start date, and an active end date.
  2. One designated default banner that has no date range and is always eligible to show.
Core logic
  1. On page load, check today's date against every campaign's active date range.
  2. If exactly one campaign is active, show it.
  3. If more than one campaign is active at once, show the one with the soonest end date, unless a manual priority order has been set, in which case that order wins.
  4. If no campaign is active, show the default banner. The page must never render with no banner at all.
  5. Campaign banners should go live ahead of the occasion, not on the day itself. Mia's own order data shows purchases peaking 8 to 11 days before Rakhi and Valentine's Day, so the campaign's start date should be set roughly two to three weeks ahead of the occasion, not the occasion date itself.
Edge cases
  • Day after an occasion: the campaign must expire automatically at its end date. Nobody should have to manually take a banner down the morning after Rakhi.
  • Overlapping campaigns: if two campaigns are scheduled for the same window by mistake, the system needs a defined tiebreak (soonest end date, or manual priority) rather than picking one at random or showing both.
  • CTA destinations per campaign: the secondary CTA should be configurable per campaign, not hardcoded to "Shop Gold Coins" always. During a Rakhi campaign it might need to point to a Rakhi-specific collection instead of the generic coins page.
Open decision

Should the banner also vary by region (for example a South-India-specific festival)? If this is in scope, it needs a location signal (pincode or detected region) added to the matching logic above. If it's out of scope for this phase, say so explicitly so nobody builds it partially by accident.

2

Gift Finder (Recommendation Engine)

▾
Purpose

Three inputs (Recipient, Occasion, Budget) produce a shortlist of around six products. This is the highest-traffic decision point on the page, the logic needs to be exact, not "roughly filter the catalogue."

Data needed
  1. Every product needs three tag fields in the catalogue: which recipient relationships it suits (a product can have more than one), which occasions it suits (also more than one), and its price.
  2. A "self-gift" tag set, separate from the relationship tags, for when Recipient is set to Self.
  3. Stock status and rating, both already used elsewhere on the page, are needed here too for ranking.
Core logic, matching
  1. Filter the catalogue to products within the selected budget range. This is a hard rule, never show a product outside the stated budget.
  2. Within that budget-filtered set, look for products tagged with both the selected recipient and the selected occasion.
  3. If that exact match returns six or more in-stock products, rank them (see ranking rule below) and show the top six.
  4. If it returns fewer than six, relax the occasion tag first, keep recipient and budget fixed, and pull products tagged for that recipient across any occasion to fill the remaining slots.
  5. If still short of six, widen the budget band to the next tier up only, never downward, since showing something cheaper than requested undermines the gift.
  6. If still short of six after that, fall back to top-rated or bestseller products for that recipient regardless of budget or occasion tag, and label this fallback set differently on screen (for example "You might also like" rather than presenting it as an exact match).
  7. The system should never return zero results. The absolute fallback is site-wide bestsellers.
Core logic, ranking

When more than six products qualify, decide which six to show using this order: in-stock items only, then highest rating, then a "Most Gifted" tag as a tiebreaker. Also apply a diversity rule, no more than two products from the same sub-category (for example, not six near-identical rings), so the shortlist doesn't read as repetitive.

Edge cases
  • Recipient = Self: should route to the self-gift tag set entirely, not the general relationship tags, and the surrounding copy (currently written toward gifting someone else) needs a self-gift variant.
  • Occasion = "Just Because": needs its own real tag on products, not a silent fallback to "no occasion filter," otherwise it behaves inconsistently with every other occasion option.
  • Highest budget tier (for example "₹50,000+"): should only apply a lower bound, no upper limit filter.
  • Stock changes after the shortlist is shown: if a shown product sells out before the visitor adds it to cart, the card should be replaced with the next-best match automatically, not left as a dead Add to Cart button.
  • Returning visitor: should the quiz reset every visit, or remember the last selection? Default should be to reset each session, except where a visitor has arrived from a reminder email that already knows their recipient and occasion (see the date-reminder module below), in which case skip straight to results.
  • Shareable results: since sharing the shortlist over WhatsApp is a core behaviour we're designing for, the result set needs a persistent, shareable link that reopens the same six products, not a blank quiz, when someone else opens it.
3

Shop By Category & Product Cards

▾
Purpose

Category tiles feeding into a product grid. Card-level badges, ratings, price and stock indicators need explicit rules, not manual per-product decisions.

Core logic, badges
  1. Only one badge shows per card, even if a product qualifies for more than one. Priority order: Editor's Pick first (manually set by the merchandising team), then Most Gifted, then Bestseller, then New In.
  2. Most Gifted: top percentage of products by gifting-tagged order volume in a trailing 90-day window.
  3. Bestseller: top percentage by total sales in a trailing 30-day window.
  4. New In: added to the catalogue within a defined recent window (for example the last 30 days).
Core logic, stock and pricing
  1. "Only X left in stock" should only display when live stock is at or below a set threshold (for example 3 units), pulled from real inventory, and must disappear the moment stock goes above that threshold.
  2. Displayed price must already include the number shown as "incl. of taxes." Confirm this matches exactly what appears at checkout, a mismatch between card price and checkout price is a common and damaging bug in this category.
  3. If gold-priced products update daily with the live gold rate plus fixed making charges, that repricing needs to run on a defined schedule (for example once daily at a fixed time) so the price shown on the card, on the product page, and at checkout are never out of sync with each other.
Edge cases
  • Out of stock entirely: the Add to Cart button should convert to "Notify Me" rather than remaining clickable and failing.
  • Default sort order: recommend defaulting to Most Gifted or Bestseller rather than New Arrivals, since a gifting buyer is generally looking for a proven choice, not the newest addition.
4

Ring Sizer Modal

▾
Purpose

Triggered from Add to Cart, but only on ring products, offering a free sizer mailed in advance if the buyer doesn't know the recipient's size.

Core logic
  1. Trigger condition must check the product's category tag specifically. A generic "fires on any Add to Cart" trigger will incorrectly show this modal on necklaces and earrings too.
  2. If the visitor selects "I know the size," proceed to a normal size selector and checkout as usual.
  3. If the visitor selects "I don't know the size," the flow needs a clear decision: does checkout complete now with sizing confirmed later through a follow-up contact, or does the item sit in a held state until the sizer is mailed and a size is confirmed? This changes both the order-management workflow and the customer messaging, and needs to be settled before build, not discovered during QA.
Edge cases
  • Visitor requests a free sizer but never returns to confirm a size, needs a defined follow-up cadence (for example a reminder after 5 days) rather than the order sitting indefinitely with no owner.
  • Address for mailing the sizer needs validation before the request is accepted, an undeliverable address defeats the entire feature.
5

"Left It Late?" Module

▾
Purpose

Gold rate calculator plus fast-format rescue paths (coins, gift card) for a visitor short on time.

Core logic, gold rate
  1. Rate needs to come from a live feed (24KT, 22KT, 18KT per gram), refreshed on a defined interval, not hardcoded or manually updated.
  2. The calculator is simple multiplication (grams entered times the selected karat's rate), but input needs validation, no negative numbers, no non-numeric entry, and a sensible cap so nobody can enter an absurd value.
  3. State clearly, as the live page already does, that the rate is based on 999 purity and GST is extra, so the number shown always matches what the visitor is quoted at checkout.
Core logic, express delivery claims
  1. Any same-day or "till 6pm" claim must check the actual current time in IST against a defined cutoff, not rely on the visitor's device clock, and must automatically switch to next-available delivery messaging the moment the cutoff passes.
  2. Same-day or next-day claims should only display if the visitor's pincode is confirmed serviceable at that speed. Tie this to the same pincode-serviceability check used elsewhere on the page, don't duplicate the logic separately here.
Edge cases
  • Exact cutoff boundary (6:00:00pm) needs a defined rule, inclusive or exclusive, stated explicitly rather than left to whatever the code happens to do.
  • Gold rate API temporarily unavailable, the module needs a fallback (for example, show the last successfully fetched rate with a timestamp) rather than displaying a blank or broken calculator.
6

Timeless Favourites (Tabs)

▾
Purpose

One merchandising section covering Most Gifted, Best Sellers, New Arrivals, plus karat and weight filters.

Core logic
  1. Decide explicitly whether tabs are mutually exclusive (only one active filter at a time) or combinable (for example Best Sellers plus Under 2g together). This changes how the underlying query is built and should be settled before development starts, not left to whichever is easier to code.
Edge cases
  • A combined filter (for example New Arrivals plus 22 Karat) returns zero live matches, needs a defined empty-state message rather than a blank grid.
7

Six Touches

▾
Purpose

Mostly static, CMS-managed content. Two of the six touches carry real logic worth calling out.

Core logic
  1. Exact delivery date selection: the date picker must only allow dates that are actually achievable given processing and shipping lead time for the visitor's pincode. Don't let someone select a date the business can't hit, that becomes a broken promise at fulfilment, not a UI problem.
  2. Insurance up to a stated cap: confirm this figure against the highest-priced SKU in the catalogue. If any product exceeds the stated cap, either raise the cap or state it differently for high-value items, so the guarantee is never technically false for a subset of products.
8

Compare Tool

▾
Purpose

Side-by-side comparison of a small number of shortlisted products.

Core logic
  1. Cap the comparison at a fixed number of products (2 to 3), and decide the exact number before build.
  2. Define a fixed attribute set to compare (metal, stone, weight, price, rating). For attributes that don't apply to every product type (for example ring size doesn't apply to a necklace), show a clear "not applicable" rather than a blank cell.
Edge cases
  • Visitor tries to add a product beyond the cap, needs a defined response, block with a message, or replace the oldest item automatically. Pick one and be consistent.
  • Comparing across very different product types (a ring against a necklace), decide whether this is even allowed, or whether Compare should be restricted to same-category items only.
  • Decide whether the comparison selection persists if the visitor navigates away and comes back, or resets each session.
9

Gift Card Builder

▾
Purpose

Live-updating gift card preview with amount, recipient name, message, and delivery date.

Core logic
  1. Message field needs an enforced character limit with a live counter, and the input must be sanitised before being rendered back into the live preview, since it's user-entered text being displayed on screen.
  2. Delivery date picker must block past dates and respect whatever minimum lead time applies, likely near-instant for a digital card, but this should be confirmed rather than assumed.
  3. Custom amount entry (if offered alongside fixed tiers) needs a defined minimum and maximum.
Open decision

Does the personal message field need any content moderation? It's a private message between giver and a known recipient rather than public content, so risk is likely low, but worth a explicit sign-off from legal or brand rather than assuming it's fine.

10

Exit-Intent Modal

▾
Core logic
  1. On desktop, trigger on mouse movement leaving the top of the viewport. Mouse-based exit intent does not work on touch devices, so mobile needs a separate trigger, for example a defined idle-time threshold or a back-button or tab-switch event.
  2. Fire once per session maximum. Do not re-trigger repeatedly if the visitor keeps scrolling back up.
  3. Suppress entirely if the visitor has already added an item to cart or completed a purchase in the current session, don't interrupt someone who is already converting.
11

"Never Miss A Date" Reminder Capture

▾
Purpose

Captures a recipient's occasion date so the brand can reach back out ahead of it next year, explicitly capped at two reminders a year per captured date.

Core logic
  1. Store the captured date along with explicit consent to be contacted about it.
  2. Schedule exactly two touchpoints per year tied to that date, for example around 12 days ahead, matching the order-ahead pattern already seen in Mia's own data, not more than that.
  3. Provide a clean way to opt out of a specific reminder without opting out of the account entirely.
Edge cases
  • Same visitor submits a second date for the same relationship (for example updates a birthday), decide whether this overwrites the earlier entry or creates a duplicate, overwriting is almost certainly correct here.
  • Visitor submits multiple different relationships (a mother's birthday and a sister's anniversary), each should be tracked and reminded independently, not merged into one entry.

02Cross-Cutting Concerns

Rules that apply across the whole page, not to any single section. Worth agreeing once, rather than re-deciding differently inside each module.

Gold rate must be a single source of truth

▾

The rate shown in the top utility bar, the "Left It Late" calculator, and any gold-priced product must all read from the same live feed and update on the same schedule. If these drift out of sync even briefly, the page will show two different prices for gold at the same moment, which is a serious credibility problem for this category specifically.

Timezone handling

▾

Anything date or cutoff related (same-day dispatch cutoff, delivery date picker, reminder scheduling) must calculate against a fixed IST server time, never the visitor's device clock, which cannot be trusted to be correct or set to the right timezone.

Loading and empty states

▾

Every section that depends on a live data call (Gift Finder results, product grid, gold rate) needs a defined loading state while the call is in flight, and a defined empty state for when a filter or search genuinely returns nothing. Neither should be left to default browser behaviour.

Mobile parity

▾

The majority of traffic to this page is mobile. Every interactive behaviour built for desktop (hover states, exit-intent, the compare tray, modals) needs an explicit mobile equivalent designed and tested, not assumed to translate automatically from a desktop interaction pattern.

Currency handling

▾

If a currency toggle (INR / Dollar) is in scope, every price on the page, including the gold-rate calculator, needs to convert consistently and simultaneously when the toggle is switched, not just the main product prices.
